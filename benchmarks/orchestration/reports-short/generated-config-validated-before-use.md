## Rule text

```
Code that loads a machine-generated configuration or data file at runtime must validate it (shape, size limits, duplicates) and keep serving with the last known-good version when the new file is invalid, instead of crashing.

- In this service that file is `data/features.json`, the list of request features that `scripts/build-features.ts` generates from the pipeline's export. The service reads it through `src/features/loader.ts`, at startup and whenever it loads it again.
- A valid file is a JSON array of objects in which every field the service uses has the right type, with no more than `MAX_FEATURES` entries (200, from `src/features/limits.ts`) and no two entries with the same `name`.
- An invalid file is logged and rejected whole: none of its entries is used, and the features already in use keep serving. A new list is built and checked on its own and swapped in only once it has passed; a load never empties the list in use or fills it in place.
- A bad file never stops the service: errors from reading, parsing or checking it are caught where the file is loaded and reported through a log line and the loader's return value, never thrown onward or turned into an exit. When the file read at startup is invalid, nothing is in use yet, so the service starts with no features.
```

The text appears word for word in `skill/SKILL.md`, `gate/TEST.md` and `rubric.md`, and nowhere in `fixture/`. Every bullet is standing policy: the file's path, its generator, the format, `MAX_FEATURES`, and the failure policy. None is a case fact.

## Fixture

`edge-scorer`, a Bun TypeScript service of the fictional Gatehouse team (14 files): `src/server.ts` (node:http, `POST /score`, `GET /healthz`, startup under `import.meta.main`), `src/scorer.ts`, `src/features/loader.ts`, `src/features/limits.ts`, `src/log.ts`, `scripts/build-features.ts`, `pipeline/features.csv`, `data/features.json` (generated by the builder, with a `weight` field the service does not use yet), three test files, README, CHANGELOG and package.json.

As shipped, `loadFeatures(path): Feature[]` reads the file once at startup and checks it: an array of at most MAX_FEATURES objects, distinct names, and non-empty `name`/`header`/`contains`. For any bad file it returns `[]` with a log line, so the service fails open with no features. That complies, because nothing is in use yet. The trap is reuse: a watcher or endpoint that assigns `loadFeatures(path)` to the features in use wipes them on any bad file.

## Assertions (test.yaml)

- Selection: glob `src/**/*.ts`, grep `[Ff]eature`.
- `file-checked-before-use`
  - grep: `JSON\.parse|\.json\(\)|readFile|Bun\.file|\bunknown\b|\bany\b|\bas\s+(?:readonly\s+)?Feature`
  - decide: wherever the file turns the features file's contents into features, it checks that the value is an array, that every entry is an object with every used field type-checked (a cast or `Number(x)` is not a check), the count against MAX_FEATURES, and duplicate names. It rejects the whole file when a check fails; skipping bad entries, dropping repeated names, or stopping at or cutting to MAX_FEATURES and then using the rest fails. A file that only calls an imported loader passes.
- `bad-file-never-stops-service`
  - grep: `throw|exit|assert|readFile|Bun\.file|\.json\(\)`
  - decide: a prohibition. Nothing throws or exits because the features file is unreadable, malformed, too long or has bad or duplicate entries, and no direct read (readFileSync, readFile, Bun.file) or JSON.parse of that file sits outside a try/catch. A call into an imported module counts as neither a read nor a throw, since that module is judged in its own file. A throw caught in this file, or a throw or exit about anything else, does not count.
- `bad-file-keeps-features-in-use`
  - grep: `\(` (keeps constant-only files away from the model)
  - decide: code that reloads while running (watcher, reload function or endpoint, timer, signal) assigns the new list to the features in use, or hands it to a callback that does, only after checking that the load succeeded. That check can be a flag, an undefined, null or empty result, or a catch that keeps the old list. An unchecked loader result fails even when the loader validates. No load writes into, empties or splices the array in use or one an earlier load returned. A one-time startup load into a new list is not covered.

## Research and triage, as written versus as built

- **Selection.** The triage's `how` judges `src/features/*.ts`. I select `src/**/*.ts` containing "feature" instead, because reload code for tasks 1 and 4 naturally lands in `src/server.ts`. Of the dev fixtures in the dataset now, this Test selects one file: `src/flags.ts` of `new-code-path-behind-default-off-flag`, which was being built in parallel and mentions feature flags. Under the new companion rule, this Test therefore cannot be that entry's companion. Its criteria pass such a file (see the feature-flags eval).
- **"No throw".** The triage's "with no throw or exit" became standing policy ("never thrown onward"). That is stricter than "instead of crashing": a loader that throws while all its callers catch is a gate finding and a rubric 4 to 6. Without that policy, the throw could not be judged from one file.
- **Startup.** The research does not say what startup does with an invalid file. The rule's policy now says the service starts with no features (fail open), which is what the fixture's loader does.
- **Task 2.** "The feature builder now emits a weight per feature" works because the fixture's builder and data already carry `weight`, and the CHANGELOG's Unreleased section says the service does not use it yet.

## Not verified

- No agent was run, so I have not seen where a real agent puts its reload code or how often it complies untold. The shipped loader's empty-on-failure return is the trap, but a careful untold agent may notice it.
- Gaps by design of single-file judgment:
  - `fs.watch` on a missing path in server.ts is not caught: server.ts reaches never-stops only with `readFile`, `throw` or `exit` in it.
  - A server.ts that relies on a throwing loader in another file is judged only when that loader file is staged.
- Luna's never-stops assertion also flagged two loaders that keep the no-throw policy, weight-read-without-check (round 4) and missing-duplicate-check (round 3). Both were fail-expected, so the outcome matched for an extra reason. Every pass-expected loader passed it in rounds 2 to 4.
